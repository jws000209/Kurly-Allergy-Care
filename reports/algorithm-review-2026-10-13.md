검증일: 2026-10-13 (한국 시간). 대상: GitHub `jws000209/Kurly-Allergy-Care`, `main`, 커밋 `5e80ef0e558a247e1130191ac63d7c7ae2a985b4`.

## 평가

기본적인 추천·필터·예산 처리와 재검증 구조는 동작한다. 하지만 **요청에서 알레르겐을 빠뜨린 뒤 그 빠진 조건으로 재검증하는 문제**, **영어 원재료·판정 근거 부족을 PASS로 처리하는 문제**를 재현했다. 현재 테스트 44개 통과만으로 사용자의 요구 전체가 충족된다고 판단할 수 없다. 우선 이 누락 경로를 막고 예외 시험을 회귀 테스트에 추가해야 한다.

## 실제 알고리즘

1. 확장은 `https://www.kurly.com/*`에 content script를 실행하고 Shadow DOM 패널을 표시한다. 컬리 상단 표시 이름을 읽어 같은 이름의 로컬 계정에 연결한다. 이 방식은 정식 계정 인증이 아니다.
2. 프로필에는 이름·관계·순서·별칭, 현재 지원하는 19종 성분, 엄격 모드를 저장한다. 요청에서 사람을 언급하면 해당 프로필을 우선하고, 없으면 선택한 프로필, 그다음 직전 대화의 대상을 사용한다. 여러 대상의 회피 성분은 합집합이다. 한 대상이라도 엄격 모드이면 합집합 전체에 엄격 모드를 적용한다.
3. `intent.py`가 자연어를 action, 상품명·분류, 예산, 개수, 대상, 추가 회피 성분, 상황 등의 구조로 바꾼다. 키가 있으면 LangChain 구조화 출력과 모델 대체를 사용하고, 없거나 실패하면 정규식·고정 어휘 파서로 처리한다.
4. LangGraph는 `parse_intent → resolve_conditions → build_cart / edit_cart / answer / ask_profile → revalidate → respond → remember` 흐름으로 실행한다. 상태는 계정별 `user_id:thread_id`로 분리되지만 메모리 저장이므로 서버 재시작 시 사라진다.
5. 후보는 로컬 SQLite 상품 DB에서 찾는다. 초기 시드는 수집된 컬리 상품 4,062개다. 컬리 검색 결과를 매 요청마다 실시간 수집하는 구조는 아니다. 방문한 상품은 `__NEXT_DATA__`와 화면의 알레르기 표시문으로 읽어 저장한다. 이 경로에는 원재료 이미지 OCR 판정이 연결되어 있지 않다. 별도 `label_ocr/` 도구가 있다는 사실과 서비스 판정에 연결됐다는 사실은 구분해야 한다.
6. `extractor.py`는 19종 한국어 사전·동의어·오탐 방지 표현과 일부 오탈자 보정으로 함유/혼입 성분을 추출한다. `rule_engine.py`는 근거 부족이면 UNVERIFIED, 회피 성분 함유이면 BLOCK, 혼입은 엄격 모드에서 BLOCK, 나머지는 PASS로 판정한다. BLOCK과 UNVERIFIED는 자동 추천 후보에서 제외한다.
7. 통과 후보에는 상품명·분류 관련도, 상황, 옵션 필요 여부, 실제 상품 여부, 개인화, 후기 수·판매량 순위를 적용한다. 아이템 협업은 상품×사용자 코사인 유사도와 상위 20개 경험 상품의 가중 평균, 함께 구매는 실제 구매자들의 다른 구매 비율, 콘텐츠는 TF-IDF·코사인이다. 혼합 가중치는 각각 40%·30%·30%이며 양수 근거만 재정규화한다. 행동은 조회 1·선호 3·담기 4·구매 5이며 중복 행동을 가산하지 않는다. 구매 데이터가 없으면 함께 구매 추천은 작동 근거가 없고 콘텐츠/인기도로 대체된다.
8. LLM이 활성화되면 상위 25개 PASS 후보 안에서 상품을 추가 선택한다. 후보 밖 번호와 중복을 버리고 코드가 예산·개수를 다시 맞춘다. 마지막에 DB의 상품을 다시 읽어 알레르기 판정을 반복한다. 상품 수는 서로 다른 상품 항목 수이며, 가격은 단가×최소 구매 수량이다.
9. 실제 장바구니 추가는 사용자가 버튼을 누르면 별도 상품 탭에서 컬리 자체 버튼을 누르는 방식이다. 요청만으로 5개가 실제 컬리 장바구니에 들어가는 것은 아니다. 구매 완료 이력은 확장에서 자동 수집하지 않는다.

**현재 알레르기 판정에 생성형 AI·RAG와 XLSX 39종 사전은 연결되어 있지 않다.** LLM은 조건 해석·후보 선택·일반 응답에 쓰이며, 알레르기 판정은 19종 규칙 엔진이 담당한다.

## 재현된 문제와 수정 우선순위

### P1: 수정 요청의 추가 회피 조건 누락

알류 프로필로 `만두 5개`를 요청한 뒤 `우유 없이 더 저렴하게`를 보냈다. 응답의 회피 조건은 계속 `['알류']`였고 우유는 추가되지 않았다. 추천에 **우유 함유 치킨너겟과 치킨텐더**가 포함되었다.

원인: `intent.py:390–407`의 수정 action 분기가 추가 회피 성분을 추출하는 `:409–414`보다 먼저 return한다. 재검증도 누락된 회피 조건을 사용하기 때문에 이 문제를 막지 못한다. 수정 action과 관계없이 공통 제약을 먼저 파싱하고, 기존 조건과 합쳐야 한다. LLM 실패 시 규칙 파서 대체에서도 재현 가능한 결함이다.

또한 저렴한 상품을 찾을 때 기존 상품의 `치킨/피자/핫도그/만두` 같은 묶인 소분류만 사용해 만두 대신 치킨이 들어간다. 비용 절감 시에도 원래 상품 유형을 유지해야 한다.

### P1: 읽지 못한 원재료를 PASS로 처리

우유 프로필에 `ingredients='milk, wheat flour'`를 입력했을 때 contains가 빈 목록이고 PASS였다. `ingredients='상세페이지 참고'`도 PASS였다. 반면 동일한 안내문이 allergy_label 필드에 있으면 UNVERIFIED였다.

원인: 한국어 사전과 `extractor.py:103`의 `bool(ingredients)` 근거 판정이다. 원재료 문자열이 비어 있지 않다는 사실만으로 판정 가능하다고 본다. 인식하지 못한 언어·안내문·불완전 텍스트는 UNVERIFIED로 처리하고, 지원하는 언어의 근거를 확보한 뒤 PASS를 허용해야 한다. 한영 XLSX 사전 연결은 후속 구현이며 현재 해결책으로 적용되었다고 쓸 수 없다.

### P1: 지원하지 않는 회피 성분을 대화에서 조용히 버림

`아몬드 없이 간식 5개`에서 추가 회피 목록은 빈 값이고 알류·우유 조건만으로 5개를 추천했다. 아몬드 프로필 API 등록은 422로 거부하지만, 대화에서는 미지원 안내가 없다. 실제 아몬드 함유 상품이 나왔다는 주장은 하지 않는다. 재현된 것은 **요청한 제약 자체의 소실**이다.

`normalize_allergen`, `_clean`, 규칙 파서가 19종 밖의 성분을 지원하지 않는다. 미지원 성분을 사용자가 요청하면 추천 전에 적용 불가를 알리고 확인하도록 해야 한다. 장기적으로 39종 사전과 프로필·API·판정·검색·재검증을 함께 연결해야 한다.

### P1: 프로필 변경 후 과거 추천의 담기 버튼에 재검증 경로 없음 (코드 확인)

`extension/content.js:557`의 프로필 토글과 `:251`의 프로필 저장은 현재 페이지 상품을 다시 판정하지만 과거 추천 카드를 재검증하지 않는다. `:363`의 담기 함수는 상품 ID로 작업 탭을 열 뿐 현재 프로필과 상품을 서버에서 다시 검사하지 않는다. 따라서 이전 프로필 기준 카드로 새 프로필에서도 담기를 요청할 수 있는 경로가 있다.

이 항목은 브라우저 UI 재현 없이 코드에서 확인한 경로다. 선택·프로필 변경 시 이전 카드 상태를 갱신하고, 실제 담기 직전에 현재 프로필·상품 정보로 서버 검증을 통과하도록 해야 한다. 서버의 대화 재검증만으로는 버튼 클릭을 보호하지 못한다.

### P2: 모르는 상품명을 일반 추천으로 바꿈

`사프란 5개 추천해줘`가 검색 조건 `terms=[]`로 바뀌고 두부·애호박·아보카도·감자·대파를 추천했다. 고정 어휘 목록에 없는 상품명이 파서에서 소실되어, 뒤의 missing_terms 검사에도 도달하지 않는다. 원문의 상품명 또는 미해석 토큰을 보존하고 모르는 종류는 되물어야 한다.

### P2: 불완전한 페이지 정보가 기존 상품 데이터를 지움

시험 DB에서 마드렌 상품의 가격 16,900원·베이커리 분류·밀/계란/대두/우유 표시를 저장해 둔 상태로, 같은 ID에 가격 null·빈 분류·빈 표시를 `/api/check`로 저장했다. 가격·분류·표시가 모두 사라지고 verified=false가 됐다. 실제 추출 실패 시 후보가 빠지거나 가격 계산에 영향을 줄 수 있다.

`db.py:231–234`는 해당 필드를 빈 값으로 덮어쓴다. 필드별 출처·갱신 우선순위와 마지막으로 확인된 유효값을 보존하고, 알레르기 근거의 신뢰 상태를 별도로 관리해야 한다.

### P2: 판정 근거·수량·부정 표현의 정확한 안내

- 전체 시드 4,062개가 verified=true였지만, 이 중 1,010개는 실제 알레르기 표시 확인이 아니라 원물·단순 구성이라는 팀 판단용 표식이다. 기존 코드가 사유 문자열로 이를 구분하는 점은 좋지만, 추천 카드에서도 근거 수준이 일관되게 보이도록 해야 한다. 현재 `itemRows`는 이름·가격·혼입 주의만 표시한다.
- `만두 5개`의 개수는 SKU/상품 항목 5개다. 시험에서는 최소 주문 수량 합이 7이었고 실제 포장 안의 만두 개수는 계산하지 않는다. “5종 추천”인지 “같은 상품 5팩 구매”인지 구분해 물어야 한다.
- `만두 0개`는 기본값으로 5개를 추천하고 `만두 -1개`는 1개로 해석했다. 개수의 최소·최대 범위 검증을 추가해야 한다.
- `우유 미함유`는 우유 함유로 추출되어 BLOCK됐다. 부정 표현의 문맥 처리가 없다. 근거 검토를 거쳐 오탐을 줄일 필요가 있다.
- 이름 기반 계정에 인증이 없고 프로필 수정/삭제는 ID만 받는다. 계정별 thread 분리는 인증·소유권 검증을 대체하지 않는다. 실제 계정 배포 전 보완 항목이다.
