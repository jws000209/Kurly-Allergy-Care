# situations.py 점검 및 실제 Luna 테스트

2026-10-14. 이번 작업은 점검이며 구현 코드는 변경하지 않았습니다. 실제 API에 합성 장보기 문장 3개를 보냈으며 DB 쓰기나 실제 장바구니 작업은 하지 않았습니다. 키 내용은 출력하지 않았습니다.

## 실제 API 결과

모든 호출의 parser=llm, model=openai:gpt-6-luna.

| 입력 | LLM 상황 | build 결과 |
|---|---|---|
| 소풍 아니고 캠핑에서 먹을 라면 추천해줘 | 캠핑 | 캠핑 |
| 다이어트 안 해. 치즈 간식 추천해줘 | 없음 | 없음 |
| 도시락 반찬 2개 추천해줘 | 없음 | 없음 |

이 3회에서 LLM 상황 오해석은 관찰되지 않았습니다. 반복 안정성·추천 품질·지연 시간의 대표성은 검증하지 않았습니다.

## 코드에서 재현한 충돌

1. find_preset은 부분 문자열과 PRESETS 순서로 먼저 걸린 상황을 선택합니다. 같은 문장의 규칙 경로 결과는 위 세 사례에 각각 소풍/다이어트/소풍입니다. 부정·명시 우선순위가 없습니다.
2. build('생일 파티')는 생일보다 먼저 파티 별칭이 걸려 손님상이 됩니다. 전달된 상황 표현 자체를 다른 상황으로 변경할 수 있습니다.
3. intent._ground의 조건은 '선택한 상황의 원문 근거'가 아니라 '어떤 프리셋이든 원문에서 발견되는지'도 인정합니다. 합성 캠핑 의도를 생일 요청에 넣어도 캠핑이 유지됩니다. 이것은 코드 재현이며 실호출에서 같은 오해석이 나왔다는 뜻은 아닙니다.
4. cart_composer.search는 상황 제외어를 상품명 부분 문자열로 하드 필터링합니다. 소풍의 '탕'은 '소풍용 사탕'도 제외합니다. 컵라면처럼 명시 요청한 종류도 소풍 제외어 때문에 selector에 도달하지 못할 수 있습니다.
5. selector에는 situation.name만 전달되고 prefer/avoid/why/source는 전달되지 않습니다. LLM은 코드의 실제 후보 필터 기준을 확인할 수 없습니다.
6. 알려진 상황은 LLM 제안 prefer/avoid를 전부 무시합니다. 미등록 상황은 같은 단어가 prefer/avoid 양쪽에 있어도 충돌을 정리하지 않습니다.
7. selector 프롬프트는 후보를 Rule Engine 검증 완료로 설명하지만 현재 경로는 로컬 후보 게이트 뒤 별도 GPT RAG 재검증입니다. 안전 판단을 하지 말라는 지침은 있으나 설명은 실제 처리 단계와 다릅니다.

## 권장 수정 순서

- 원문에서 긍정된 상황만 추출하고 명시된 상황과 혼합/부정 표현의 충돌을 처리.
- _ground는 선택한 상황 자체와 원문을 대조. 다른 상황의 발견을 근거로 인정하지 않음.
- 취향 프리셋은 순위 우선/감점 중심으로 사용하고 명시 요청과 충돌하면 조정. 알레르기 차단과 분리 유지.
- 한 글자 제외어의 부분 일치 제거. 목적어 도시락·식단 같은 표현을 상황으로 일괄 승격하지 않음.
- selector에 정리된 상황 기준과 적용 이유를 제공. 최종 검증 단계 설명을 현재 RAG 흐름에 맞춤.
- 회귀 평가에 부정 상황·복합 행사·명시 상품 충돌·같은 prefer/avoid를 추가.
